# Add-to-Cart Redirect Source Study

## Scope

Investigate the live add-to-cart response that reportedly contains:

```text
/proxy/8000/proxy/8000/cart/
```

The diagnostic must determine whether Django itself creates that duplicated `Location` header at the add-to-cart source, and whether there is more than one redirect hop. It must not change cart behavior or implement a permanent prefix fix yet.

## Current Codebase

The authenticated add-to-cart path is implemented in `core.views.product_detail`. For a valid POST, it validates the quantity, writes the cart item, and executes exactly one redirect:

```python
return redirect('cart')
```

There is no second redirect in that view. The cart view is directly mapped to `cart/` and does not redirect authenticated users. The product detail form action is generated with `{% url 'product-detail' product.pk %}` and does not manually concatenate `/proxy/8000`.

The branch currently contains a temporary `/debug-scriptname/` endpoint for the user to inspect live request metadata. The user reports that live `SCRIPT_NAME`, `PATH`, and `PATH_INFO` match the local baseline and that no forwarded-prefix headers are present. The raw live add-to-cart `Location` header still duplicates the prefix, so source-level logging is needed.

## Feasibility

Django's `redirect()` helper resolves the named `cart` URL before constructing the response. The view can temporarily assign that response to a variable, log the resulting `Location` header, and return the unchanged response. This captures the exact value produced inside the view before a browser or proxy follows it.

A module logger is preferable to `print()` because it uses Django's existing logging pipeline and can be removed cleanly. The temporary log should include only the route name, request path, `SCRIPT_NAME`, and generated `Location`; it must not include cookies, credentials, session data, or request bodies.

## Diagnostic Approach

1. Add a temporary logger to `core.views`.
2. Replace the direct `return redirect('cart')` with:
   - construct the redirect response;
   - log its `Location` and safe request script metadata;
   - return the same response unchanged.
3. Keep the form action unchanged and verify its rendered HTML locally. It should be one URL generated by Django's `{% url %}` tag.
4. Use the existing temporary `/debug-scriptname/` endpoint to confirm the live process is serving the diagnostic branch.
5. Trigger one valid add-to-cart POST through the Coderange UI and capture the source log line from the live server output.
6. Compare the logged source `Location` with the raw browser response and note whether the duplicate exists before any redirect hop.
7. Remove the temporary logging and diagnostic endpoint after the live output is supplied. Do not implement the permanent fix until the source value is known.

## Redirect-Hops Analysis

- Authenticated valid add: product detail POST -> one `302` to cart. There is no expected intermediate redirect.
- Anonymous add: `login_required` may produce one redirect to login before the product-detail view runs; this is a separate access-control flow.
- Invalid quantity: product detail returns `200` with form errors and does not redirect.
- Authenticated cart GET: cart view returns `200` and does not redirect.

The source log will distinguish a Django-generated duplicate from a later proxy/browser rewrite. If the log contains one prefix but the browser sees two, the extra prefix is outside this view. If the log contains two, the interaction between Django's script prefix and the deployment request environment must be fixed at the source.

## Risks and Cleanup

- Temporary logging may expose deployment path metadata. Mitigation: log only safe path fields and the generated `Location`.
- Logging may not be visible through the browser. Mitigation: keep the endpoint available for branch confirmation and ask the user to paste the server log line from the live environment.
- The diagnostic route must not remain deployed after the probe. Mitigation: remove it and the logger immediately after analysis.
- A source log result must not be mistaken for a permanent fix. Mitigation: create a separate study/plan for the actual settings or middleware correction once the cause is confirmed.

## Verification Strategy

- Run `python manage.py check` with the temporary logger and route present.
- Run the existing test suite; valid add tests should continue to assert the redirect target.
- Render the product detail page and confirm the form action is generated by Django and contains the configured prefix exactly once.
- Trigger a valid live add-to-cart POST and capture the source log line.
- Compare source and browser `Location` values and count redirect responses.
- Remove temporary diagnostics and rerun `python manage.py check` and tests.
