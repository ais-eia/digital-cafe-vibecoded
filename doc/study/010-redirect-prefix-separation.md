# Redirect Prefix Separation Study

## Scope

The live raw redirect probe established that Coderange automatically adds `/proxy/8000` to redirect `Location` headers:

- Django sends `Location: /cart/`.
- Coderange returns `Location: /proxy/8000/cart/`.

The current application keeps `FORCE_SCRIPT_NAME=/proxy/8000` so Django-generated HTML links include the forwarded prefix. When application code calls `redirect('cart')`, Django reverses the named URL with that same script prefix, sends `/proxy/8000/cart/`, and Coderange adds its prefix again. The result is `/proxy/8000/proxy/8000/cart/`.

The goal is to keep prefixed URL generation for regular HTML links while making redirect responses contain an unprefixed path that Coderange can prefix exactly once.

This study does not implement the fix. The temporary raw redirect probe remains a diagnostic change until the implementation plan is approved and executed.

## Confirmed Findings

- The add-to-cart view's source response contains one prefix: `/proxy/8000/cart/`.
- A raw `HttpResponse(status=302, headers={'Location': '/cart/'})` reaches the live client as `/proxy/8000/cart/`.
- Coderange applies exactly one external prefix to raw redirect locations.
- The product-detail form action and other regular template links use Django URL reversing and need the existing prefix behavior.
- The repository contains no custom middleware that rewrites `Location` headers.
- The duplicate is caused by two independent redirect transformations: Django's `FORCE_SCRIPT_NAME` URL reversal and Coderange's redirect-prefix rewrite.

## Django Behavior and Built-In Options

`FORCE_SCRIPT_NAME` is a global URL script-prefix setting. It affects Django's URL reversing machinery, including calls made by `redirect()` when passed a view name. Django does not have a built-in setting that says “include the script prefix in template URL reversing but omit it only from HTTP `Location` headers.” From Django's perspective, a redirect target generated by `redirect('cart')` is just another reversed URL.

The existing `LOGIN_URL` and `LOGIN_REDIRECT_URL` settings also need review. If they contain `/proxy/8000`, Django's authentication redirects can be double-prefixed by Coderange in the same way. They should use unprefixed application paths when they are consumed as redirect targets, while login form actions and ordinary template links can continue using `{% url %}` and `FORCE_SCRIPT_NAME`.

There is no safe built-in `reverse(..., script_prefix='')` argument in the current Django API. Temporarily changing Django's process/thread-local script prefix around every reverse operation would be fragile and unnecessarily global. A helper should isolate that behavior and restore the original prefix in a `finally` block if that technique is selected.

## Options

### Option A: Unprefixed Redirect Helper, Retain `FORCE_SCRIPT_NAME`

Add a small application helper for redirects that reverses a named route with the script prefix temporarily set to `/`, then passes the resulting unprefixed path to Django's redirect response. For example, the add-to-cart flow would use a helper equivalent to `redirect_without_script_prefix('cart')`.

Set authentication redirect targets to unprefixed paths such as `/login/` and `/`, because Coderange will add the external prefix to those response headers. Keep `FORCE_SCRIPT_NAME` active so `{% url %}` tags in HTML continue generating `/proxy/8000/...` links.

Advantages:

- Smallest change to the existing application architecture.
- Preserves all current template URL generation.
- Makes the proxy contract explicit at redirect call sites.
- Supports named URL reversing instead of hardcoded route strings.

Risks and constraints:

- Every application redirect must use the helper, and future developers could accidentally call ordinary `redirect('name')` again.
- The helper must restore the original script prefix even if reversing fails.
- Tests must verify both the helper's unprefixed response and the regular prefixed `reverse()` behavior.
- A helper based on temporarily calling `set_script_prefix('/')` must be carefully scoped. Django's script prefix is thread-local, but the implementation should still minimize the mutation window.

### Option B: Keep `FORCE_SCRIPT_NAME`, Pass Literal Unprefixed Redirect Paths

Change redirect call sites to use literal paths such as `redirect('/cart/')`, and set login redirect settings to `/login/` and `/`.

Advantages:

- Very small implementation.
- No temporary script-prefix manipulation.

Risks and constraints:

- Hardcodes URL paths and bypasses named URL resolution.
- Route changes can silently break redirects.
- Does not scale cleanly as cart, checkout, history, and admin flows add redirects.
- Conflicts with the project's existing rule to use URL reversing for application links.

This is acceptable only as a narrowly scoped emergency fix, not the preferred design.

### Option C: Remove `FORCE_SCRIPT_NAME` and Add Prefix-Aware Template URL Generation

Unset `FORCE_SCRIPT_NAME` so all Django redirects are unprefixed, allowing Coderange to prefix them. Introduce a custom template tag or context mechanism that adds `/proxy/8000` only to HTML links and form actions.

Advantages:

- Django's built-in redirects become naturally compatible with Coderange.
- No special redirect helper is needed.

Risks and constraints:

- Every template URL needs the custom tag or context behavior, including existing and future templates.
- Built-in Django components and third-party templates would not automatically receive the prefix.
- Authentication redirects, `next` values, and server-side `reverse()` calls would need separate handling.
- It replaces a standard Django deployment mechanism with application-specific URL generation.

This is more invasive than the confirmed problem requires and risks regressions in already-verified product and login links.

## Recommendation

Use Option A: retain `FORCE_SCRIPT_NAME` for regular URL reversing, introduce a narrowly scoped named-route redirect helper for application redirects, and make authentication redirect settings unprefixed.

The helper should:

1. Capture the current script prefix.
2. Temporarily set the script prefix to `/`.
3. Reverse the named route with the normal Django URL resolver.
4. Restore the original script prefix in `finally`.
5. Return Django's normal redirect response using the unprefixed path.

The helper should support the same route arguments needed by the application and should not accept arbitrary user-controlled URLs. It should be tested with the current `/proxy/8000` configuration and with an empty local prefix.

Authentication should use unprefixed redirect targets because those settings produce HTTP `Location` headers, not HTML links. The login template should continue to use `{% url 'login' %}`, which should remain prefixed under `FORCE_SCRIPT_NAME`.

## Verification Strategy

- Test regular `reverse('home')`, `reverse('product-detail')`, and template-generated form/link actions still include `/proxy/8000`.
- Test the named-route redirect helper returns `/cart/`, not `/proxy/8000/cart/`, while `FORCE_SCRIPT_NAME` remains configured.
- Test the add-to-cart response's source `Location` is `/cart/` locally.
- Test `LOGIN_URL` and `LOGIN_REDIRECT_URL` produce unprefixed redirect targets, while the login form action remains prefixed in rendered HTML.
- Test anonymous redirects and successful login redirects under both prefix configurations.
- Run the full existing test suite and the application checks.
- Re-run the live add-to-cart flow through Coderange and verify the final `Location` is exactly `/proxy/8000/cart/`.
- Remove the temporary raw redirect probe before committing the permanent fix.
